# 추천 견적·벤치마크·자동 견적 재설계안

작성일: 2026-09-04
대상: `/recommendations`, `/benchmarks`, `/quote` 및 관련 API/Agent/DB

## 1. 결론

현재 화면에 표시되는 성능 수치는 **해상도별 실측 데이터라고 볼 수 없다**. 같은 게임의 FHD·QHD·4K 행에 동일한 FPS가 반복되는 이유는 원본 데이터가 게임당 `평균프레임` 하나만 가지고 있고, 동기화 과정에서 그 값을 세 해상도에 그대로 복사하기 때문이다. 현재 레코드는 `sampleCount=1`이며 테스트 옵션, 드라이버, 게임 버전, 평균/최저/1% low의 구분도 없다.

자동 견적도 AI가 부품을 직접 설계하는 구조가 아니다. 현재 브라우저에서 `generateDynamicQuote()`가 고정 가격대와 텍스트 기반 호환 필터로 상품을 고르고, AI 상담은 입력값 일부를 변경하는 역할만 한다. 따라서 `450만원 + AI`를 넣어도 게임용 GPU 중심의 일반 게이밍 견적이 나오는 것이 현재 구조상 자연스러운 결과다.

운영 기준에서는 다음 세 가지를 분리해야 한다.

1. **실측 성능**: 동일 조합·동일 조건에서 직접 측정된 값
2. **출처 보고값**: 출처가 해상도별로 실제 값을 제공했지만 우리 검증을 거치지 않은 값
3. **추정값**: 다른 해상도·다른 조합·모델링으로 계산한 값

이 구분 없이 모두 `실제 DB`, `실측`, `isEstimated=false`로 표시하면 서비스 신뢰도를 훼손한다.

## 2. 현재 동작 검증 결과

### 2.1 벤치마크 데이터 규모

운영 API를 읽기 전용으로 확인한 결과는 다음과 같다.

| 항목 | 현재 값 | 의미 |
|---|---:|---|
| benchmark builds | 2,199 | 수집된 빌드 행 전체 |
| 고유 CPU/GPU 조합 | 147 | 조합 후보 전체 |
| FPS가 연결된 조합 | 1 | 실제 FPS 조회가 가능한 조합 |
| benchmark games | 160 | 게임 마스터 전체 |
| FPS 원본 결과 | 462 | 154게임 × 3해상도 |
| 조합 집계 결과 | 462 | 위 FPS 원본을 조합별로 집계한 행 |
| 공개 추천 글 | 3 | 현재 게시 가능한 추천 콘텐츠 |

FPS가 연결된 유일한 조합은 빌드 표본 1개와 게임 154개를 가진 조합이다. 따라서 `147개 조합을 검증했다`고 해석하면 안 되고, 현재는 **한 조합의 데이터만 FPS 화면에 사용되고 있다**고 해석해야 한다.

`/recommendations/n`은 현재 등록된 slug가 아니어서 404를 반환한다. 실제 추천 상세에서 성능 표가 나오는 경우에도 아래와 같은 단일 벤치마크 조합의 결과를 읽는 구조다.

### 2.2 동일 FPS의 원인

현재 동기화 로직은 다음 순서로 동작한다.

1. 게임 테이블에서 `평균프레임` 하나를 읽는다.
2. FHD/QHD/UHD 열에서는 `최상옵까지 지원` 같은 지원 문구를 읽는다.
3. 세 해상도에 같은 `avgFps`를 넣는다.
4. 표시 범위는 `avgFps × 0.85 ~ avgFps × 1.15`로 만든다.

즉, FHD·QHD·UHD가 모두 `144`라면 그것은 세 해상도에서 각각 144 FPS를 측정했다는 뜻이 아니라, 게임당 평균값 144를 세 행에 복제한 것이다. 표시되는 `122~166 FPS`도 측정된 최저·최고가 아니라 임의의 표시 범위다.

현재 운영 응답에서도 동일 게임의 세 해상도 값이 같은 것을 확인했다. 예를 들어 APEX 레전드는 세 해상도 모두 `122~166 FPS`, 원본 평균은 세 행 모두 `144`다. 다른 게임도 같은 패턴을 보인다.

저장해야 할 정보가 없는 경우에는 세 행을 억지로 생성하지 말고 다음 중 하나로 처리해야 한다.

- 해상도별 값이 없으면 `resolution=UNKNOWN`인 단일 보고값으로 저장
- 지원 문구만 있으면 FPS 결과와 분리된 `resolution_capability`로 저장
- 해상도별 실측이 생긴 뒤에만 FHD/QHD/UHD FPS 행 생성

현재 브랜치의 서버 코드에 동일 버킷을 감지해 QHD/4K에 고정 배율을 적용하는 임시 로직이 있으나, 이는 실측을 복구하지 못한다. 운영 화면에서 사용하려면 `DERIVED`로 명시하고 근거와 모델 버전을 노출해야 한다.

### 2.3 견적 성능 예상의 실제 연결 상태

현재 `/quote`의 자동 견적 흐름은 다음과 같다.

```text
설문 입력
  → 브라우저에서 catalog 로드
  → generateDynamicQuote(input, catalog)
  → CPU/GPU 이름을 /benchmarks/quote-performance에 전송
  → 일치하는 조합 집계에서 성능 조회
  → quote.performance에 표시
```

현재 사용되는 조합 매칭은 CPU/GPU 모델 문자열 키워드 검색이다. 정확히 일치하는 조합이 없으면 성능을 보여주지 않는 방향은 맞지만, 모델 문자열이 같다고 해서 테스트 조건까지 같아지는 것은 아니다.

추가로 현재 `quote-performance` API는 요청의 `games`를 결과 필터로 쓰지 않고 우선 정렬에만 사용한다. 요청에 APEX 하나만 넣어도 limit 안에 다른 게임들이 함께 반환된다. 화면에서는 선택 게임이 먼저 보일 뿐, 서버가 선택 게임만 계산한 것은 아니다. 이 부분은 즉시 수정해야 한다.

### 2.4 추천 글이 3개뿐인 이유

추천 글 생성 Agent에는 몇 개의 고정 recipe가 있고, 각 recipe가 다음을 지정한다.

- CPU/GPU 포함 문자열
- 카테고리별 가격 상한
- 일부 선택 조건
- 게시글 제목/본문 템플릿

현재는 이 고정 recipe가 생성하는 게시글 수가 곧 공개 게시글 수다. 벤치마크 빌드 2,199개가 있다고 추천 글 2,199개가 자동 생성되는 구조가 아니다. 또한 추천 글 상세에서 벤치마크 게임을 연결할 때 CPU/GPU 모델 문자열로 다시 찾기 때문에, 근거 조합·샘플 수·데이터 신뢰도가 게시글에 함께 고정되지 않는다.

## 3. 새 도메인 모델

기존의 단일 `purpose`와 단일 `priority`를 아래 프로필로 확장한다.

### 3.1 WorkloadProfile

고객의 용도는 하나가 아니라 여러 작업의 묶음이다.

```ts
type WorkloadProfile = {
  workloads: Array<{
    type: 'GAMING' | 'STREAMING' | 'VIDEO_EDITING' | 'AI' | 'OFFICE' | 'DEVELOPMENT';
    weight: number; // 합계 100
    details: Record<string, unknown>;
  }>;
};
```

예시:

```json
{
  "workloads": [
    { "type": "GAMING", "weight": 50, "details": { "games": ["배틀그라운드"], "resolution": "QHD", "refreshRate": 165 } },
    { "type": "VIDEO_EDITING", "weight": 30, "details": { "software": ["Premiere Pro"], "codec": ["H.264", "H.265"], "timeline": "4K" } },
    { "type": "AI", "weight": 20, "details": { "mode": "INFERENCE", "modelSize": "13B", "quantization": "Q4" } }
  ]
}
```

게임을 선택하지 않은 AI 전용 사용자에게 해상도와 게임 질문을 강제하지 않는다. 혼합 사용자는 각 용도의 비중을 받아 CPU 코어, GPU VRAM, RAM, 저장장치와 성능 예산을 함께 배분한다.

### 3.2 BudgetProfile

현재 80~450만원 단일 슬라이더는 AI·워크스테이션 수요를 표현하지 못한다.

```ts
type BudgetProfile = {
  minimumWon: number;
  targetWon: number;
  maximumWon: number;
  includes: Array<'PARTS' | 'ASSEMBLY' | 'WINDOWS' | 'SHIPPING' | 'MONITOR'>;
  allowOverBudgetRecommendation: boolean;
};
```

450만원을 입력했을 때 AI 요구사항을 만족하는 구성이 450만원을 초과하면 게임용 PC로 몰래 대체하지 않는다. 다음 중 하나를 명시적으로 보여준다.

- 450만원 안에서 가능한 AI 구성
- 요구사항을 만족하려면 필요한 최소 금액
- 예산을 늘렸을 때의 추천 구성

### 3.3 PreferenceProfile

성능·가성비·감성·업그레이드 중 하나만 고르는 대신, 프리셋을 제공하되 내부적으로는 가중치로 저장한다.

| 프리셋 | 성능 | 가성비 | 감성 | 업그레이드 |
|---|---:|---:|---:|---:|
| 성능 우선 | 45 | 15 | 10 | 30 |
| 가성비 우선 | 25 | 45 | 10 | 20 |
| 감성 우선 | 30 | 15 | 40 | 15 |
| 업그레이드 우선 | 30 | 15 | 10 | 45 |

고급 사용자에게는 직접 조정할 수 있게 하고, 모든 견적에 `rulesetVersion`을 저장해 나중에 왜 부품이 선택되었는지 재현할 수 있게 한다.

### 3.4 StorageDemand

저장 용량은 단일 선택지가 아니라 사용 목적별 수요로 계산한다.

```ts
type StorageDemand = {
  systemGb: number;
  activeProjectGb: number;
  archiveGb: number;
  growthGbPerYear: number;
  redundancy: 'NONE' | 'MIRROR' | 'BACKUP_REQUIRED';
};
```

빠른 시스템 디스크와 대용량 작업/보관 디스크를 분리하고, 250GB·500GB·1TB·2TB·4TB·8TB·10TB 이상을 허용한다. 용량이 지나치게 크면 한 장의 SSD로 해결하지 않고 SSD/HDD/NAS/백업 필요 여부를 설명한다.

### 3.5 Evidence

성능 결과는 숫자보다 근거가 먼저다.

```ts
type PerformanceEvidence = {
  type: 'MEASURED' | 'SOURCE_REPORTED' | 'DERIVED' | 'NONE';
  confidence: 'HIGH' | 'MEDIUM' | 'LOW';
  comboMatch: 'EXACT' | 'SKU_EQUIVALENT' | 'FAMILY' | 'NONE';
  sampleCount: number;
  measuredAt?: string;
  gameVersion?: string;
  driverVersion?: string;
  preset?: string;
  upscaling?: string;
  note?: string;
};
```

`MEASURED`만 “실측”으로 부르고, `SOURCE_REPORTED`는 “보고값”, `DERIVED`는 “추정/보정”으로 표시한다.

## 4. 자동 견적 구현안

### 4.1 전체 파이프라인

```text
설문 입력
  → ProfileNormalizer
  → HardConstraintResolver
  → 호환 가능한 후보 조합 생성
  → 목적별 성능/용량/확장성 계산
  → PreferenceProfile 가중치로 점수화
  → 예산·재고·가격 신선도 검증
  → 1개가 아닌 3개 후보 생성
  → 선택 이유·부족한 요구사항·성능 근거 표시
```

### 4.2 하드 제약과 소프트 점수 분리

다음은 점수가 아니라 탈락 조건이다.

- CPU 소켓과 메인보드 소켓
- 메모리 타입과 슬롯/용량
- GPU 길이·두께와 케이스 여유
- 쿨러 높이/라디에이터와 케이스 여유
- GPU 전력과 PSU 용량·커넥터
- AI 요구 VRAM/시스템 RAM
- 필요한 저장 용량
- 현재 구매 가능한 활성 판매 단위

나머지는 점수화한다.

```text
totalScore
  = workloadFit × workloadWeight
  + performanceScore × performanceWeight
  + valueScore × valueWeight
  + upgradeScore × upgradeWeight
  + aestheticsScore × aestheticsWeight
  - budgetPenalty
  - uncertaintyPenalty
```

점수 계산은 프론트가 아니라 서버에서 수행해야 한다. 프론트는 결과와 설명을 렌더링하고, 실제 가격·재고·호환성·선택 근거는 서버가 책임진다.

### 4.3 용도별 요구사항

| 용도 | 핵심 입력 | 우선 평가할 부품 |
|---|---|---|
| 게임 | 게임, 해상도, 주사율, 옵션, RT/업스케일링 | GPU, CPU, VRAM, 냉각 |
| 방송 | 송출 해상도, 동시 게임, 인코더, 카메라 수 | GPU 인코더, CPU 코어, RAM |
| 영상 편집 | 프로그램, 타임라인, 코덱, 소스 저장량 | CPU 코어, RAM, GPU VRAM, SSD |
| AI 추론 | 모델 파라미터, 양자화, 동시 사용자, 프레임워크 | GPU VRAM, CUDA/가속기, RAM, SSD |
| AI 학습 | 모델 크기, 배치, 데이터셋, 학습 시간 | VRAM, GPU 확장, PSU, 냉각, 저장장치 |
| 사무 | 모니터 수, 문서/화상회의, 소음 | 내장 그래픽, 저전력 CPU, 안정성 |
| 개발 | IDE, 컨테이너/VM 수, 빌드 병렬도, 저장량 | CPU 코어, RAM, NVMe, 네트워크 |

AI에서는 게임 해상도와 게임 목록을 숨기거나 선택사항으로 둔다. 게임과 AI를 동시에 선택한 경우에만 두 요구사항을 workload weight로 결합한다.

### 4.4 결과는 3개 이상의 의도 있는 후보

현재처럼 하나의 결과만 “최적”이라고 표현하지 않는다. 기본 결과는 다음으로 구성한다.

1. **균형형**: 예산과 모든 workload를 균형 있게 만족
2. **성능형**: 주 workload의 목표 성능을 우선하고 부가 용도를 양보
3. **가성비/확장형**: 현재 비용을 낮추거나 향후 업그레이드 경로를 확보

각 후보에 아래 설명을 함께 저장한다.

- 예산 사용률
- 충족한 요구사항과 미충족 요구사항
- 핵심 부품을 선택한 이유
- 성능 데이터의 근거 유형·표본 수
- 가격이 변하면 다시 확인해야 하는 항목

## 5. 설문 UI 재설계

### 5.1 1단계: 예산

- 빠른 선택: 80만, 120만, 180만, 250만, 450만, 1,000만 이상
- 직접 입력: 최소/희망/최대 예산
- 조립비·윈도우·배송비·모니터 포함 여부
- `예산 내에서만`, `부족하면 필요한 금액도 안내` 선택

AI 사용자가 1,000만~5,000만원 수요를 표현할 수 있어야 하므로 상한을 450만원에 고정하지 않는다.

### 5.2 2단계: 복수 용도

카드를 여러 개 선택하고 선택한 용도마다 비중을 조정한다.

- 게임
- 방송/스트리밍
- 영상 편집
- AI 추론/학습
- 사무
- 개발/가상화

처음에는 프리셋 비중을 제공하고, “직접 조정”을 펼치면 슬라이더가 보이도록 한다. 합계는 항상 100으로 정규화한다.

### 5.3 3단계: 조건부 질문

- 게임 선택 시: 인기 게임 8개를 상단에 표시하고 검색/전체 펼치기 제공
- 게임 목록은 DB의 인기 점수·최근 선택 수·벤치마크 존재 여부로 정렬
- 해상도 질문은 게임 workload가 있을 때만 표시
- AI 선택 시: 추론/학습, 모델 크기, 양자화, 프레임워크, 동시 실행 수 질문
- 영상 선택 시: 프로그램, 작업 해상도, 코덱, 원본/캐시 용량 질문
- 개발 선택 시: 컨테이너/VM 수, 빌드 병렬도, 프로젝트 용량 질문

게임 목록 수십 개를 한 화면에 모두 노출하지 않는다. 인기 상위 목록과 검색/펼치기를 분리한다.

### 5.4 4단계: 저장장치

단일 `500GB/1TB/2TB` select를 제거하고 다음을 제공한다.

- 시스템: 250GB~2TB
- 작업 공간: 500GB~10TB+
- 보관/백업: 별도 디스크·외장/NAS 선택
- 성장량: 연간 증가 예상

### 5.5 5단계: 우선순위

프리셋을 그대로 유지하되 실제 저장값은 가중치다. 결과 화면에서 “성능 우선이라 GPU에 예산을 더 배정했습니다”, “업그레이드 우선이라 AM5/확장 슬롯을 선택했습니다”처럼 설명한다.

## 6. 벤치마크 데이터 재설계

### 6.1 저장 모델

현재 `benchmark_fps_results`에 다음 메타데이터를 추가하거나 별도 `benchmark_observations` 테이블로 분리한다.

- CPU/GPU의 표준 부품 ID 또는 정확한 SKU
- 게임 ID, 해상도, 그래픽 프리셋
- 평균 FPS, 1% low, 최저 FPS, 최고 FPS
- 샘플 수와 측정 시간
- 게임 버전, 드라이버 버전
- DLSS/FSR/XeSS/Frame Generation/RT 여부
- 데이터 유형(`MEASURED`, `SOURCE_REPORTED`, `DERIVED`)
- 원본 위치와 수집 시각(공개 응답에는 노출하지 않음)
- 검수 상태와 규칙 버전

`benchmark_combo_game_results`는 조회용 집계 테이블로 유지하되, 원본의 evidence 정보를 잃지 않게 한다.

### 6.2 수집·검수 규칙

1. 해상도별 FPS가 실제로 없으면 해상도별 행을 만들지 않는다.
2. 평균 FPS 하나에서 min/max를 임의로 만들지 않는다.
3. 다른 조합의 FPS를 가장 가까운 조합에 붙이지 않는다.
4. 제품군만 일치하면 `FAMILY` 추정으로 표시하고 “실측”으로 표시하지 않는다.
5. 표본 1개는 `sampleCount=1`, 신뢰도 `LOW`로 표시한다.
6. 조건이 다른 기록은 평균 집계하지 않고 조건별로 분리한다.
7. 실측이 없는 게임은 “데이터 없음”으로 표시한다.

### 6.3 API 계약

`POST /benchmarks/quote-performance`는 선택 게임만 반환해야 한다.

```json
{
  "combo": {
    "match": "EXACT",
    "sampleCount": 3
  },
  "items": [
    {
      "game": "APEX 레전드",
      "resolution": "QHD",
      "fps": { "avg": 144, "min": 118, "low1Percent": 101 },
      "evidence": {
        "type": "MEASURED",
        "confidence": "MEDIUM",
        "sampleCount": 3,
        "preset": "ULTRA",
        "upscaling": "OFF"
      }
    }
  ],
  "missing": []
}
```

보정값이 필요한 경우 응답을 숨기지 말고 다음처럼 명시한다.

```json
{
  "evidence": {
    "type": "DERIVED",
    "confidence": "LOW",
    "note": "FHD 실측값에서 해상도 모델로 계산한 값"
  }
}
```

화면 문구도 `실제 DB` 대신 `실측 3회`, `출처 보고값`, `해상도 추정값`, `데이터 없음`처럼 evidence에 따라 바꾼다.

### 6.4 우선 수집할 조합

처음부터 모든 147개 조합을 채우기보다 다음 매트릭스를 만든다.

- 가격대: 입문/중급/QHD 고주사율/4K/AI 워크스테이션
- CPU: 대표 게임 CPU와 작업용 멀티코어 CPU
- GPU: 각 가격대별 NVIDIA/AMD 대표 모델
- 게임: 인기 8개 + AAA 8개 + CPU 의존형 4개 + 신규 수요
- 해상도: FHD/QHD/4K
- 조건: 최소한 프리셋·업스케일링·드라이버를 고정

각 조합은 최소 3회 측정하고, 측정 불가 게임은 지원 여부와 FPS를 분리한다. 그 다음 사용자 조회 빈도가 높은 조합을 우선 확장한다.

## 7. 추천 글 생성 재설계

### 7.1 고정 recipe에서 후보군 생성으로 변경

현재의 고정 recipe 3개를 완전히 제거할 필요는 없지만, 그것만으로는 부족하다. 다음 입력으로 후보군을 만든다.

- 가격대 구간
- workload 유형
- CPU/GPU 플랫폼 조합
- 대표 게임/해상도
- preference preset
- 실제 활성 판매 단위와 가격 신선도
- 벤치마크 evidence 존재 여부

후보 생성 후 다음 중복 키를 기준으로 중복을 제거한다.

```text
purpose + budgetBand + cpuModel + gpuModel + primaryWorkload + resolution
```

가격·재고가 바뀌면 글의 부품 snapshot과 현재 가격을 비교해 자동으로 `REVIEW_REQUIRED`로 바꾼다.

### 7.2 공개 추천 콘텐츠 목표

초기 운영 목표는 3개가 아니라 다음 정도가 적절하다.

- 게임 12개: FHD/QHD/4K, 가성비/균형/성능
- 방송·영상 6개
- AI 추론·개발 6개
- 사무·저소음 3개
- 업그레이드형 3개

이것은 억지로 게시글 수를 늘리자는 뜻이 아니다. 각 글은 실제 부품·현재 가격·호환성·evidence를 만족할 때만 게시한다. 조건을 만족하지 못하면 게시글 수보다 “준비 중” 상태가 정직하다.

### 7.3 추천 상세 표시

추천 글마다 다음을 표시한다.

- 추천 목적과 workload 비중
- 목표 예산과 실제 현재 합계
- 부품별 선택 이유
- 성능 결과와 evidence 뱃지
- 표본 수와 측정 조건
- 가격 확인 시각
- 현재 재고 상태
- 주문 전 재검증 여부

내부 DB의 수집 출처·원본 URL은 운영자만 보고, 공개 API와 본문에는 노출하지 않는다. 공개 문구는 “JHS 검수 데이터”, “실측”, “보고값”, “추정”처럼 데이터 성격만 전달한다.

## 8. 구현 순서

### P0 — 즉시 수정

1. FPS가 없는 해상도 행을 실측처럼 표시하지 않기
2. `isEstimated=false`를 데이터 evidence 기반으로 변경
3. `quote-performance`에서 요청 게임만 반환
4. 동일 FPS 행에 고정 보정값을 적용하더라도 `DERIVED/LOW`로 표시
5. 추천 글 본문에서 “실측”을 쓰려면 exact combo와 evidence를 검사
6. `/recommendations/n` 같은 미등록 slug를 정상적인 목록/404 UX로 처리

### P1 — 데이터 모델과 수집

1. benchmark observation/evidence 컬럼 추가
2. 게임·해상도·옵션·드라이버·샘플 수 저장
3. 현재 462건을 재분류하여 `SOURCE_REPORTED` 또는 `UNKNOWN`으로 정정
4. 대표 조합 10~20개를 동일 조건으로 직접 검증
5. combo 집계 시 exact SKU와 family match 분리

### P2 — 자동 견적 엔진

1. `WorkloadProfile`, `BudgetProfile`, `PreferenceProfile`, `StorageDemand` DTO 추가
2. 서버에 후보 생성·호환성·가격 검증 로직 구현
3. 가격·재고·스펙 불충분 후보 제외
4. 균형형/성능형/가성비 또는 확장형 3개 생성
5. 결과에 선택 이유와 미충족 조건 저장
6. 주문 시점에는 견적 생성 시점과 별도로 가격·재고 재검증

### P3 — 설문·결과 화면

1. 복수 용도와 용도별 비중
2. AI/영상/개발 조건부 질문
3. 인기 게임 상단 + 검색 + 전체 펼치기
4. 250GB~10TB+ 저장 요구 입력
5. 우선순위 프리셋 + 고급 가중치 조정
6. 결과 후보 비교표와 evidence 뱃지

### P4 — 추천 콘텐츠 운영

1. 고정 recipe를 ruleset 기반 후보 생성기로 전환
2. 게시 전 자동 품질 게이트
3. 가격/재고 만료 시 `REVIEW_REQUIRED`
4. 콘텐츠별 성능 근거와 검수 이력 저장
5. 공개 30개 내외의 목적별 카탈로그 구축

## 9. 완료 기준

### 성능

- FHD/QHD/4K 값이 같아도 실측이라고 표시되지 않는다.
- 선택한 게임만 `quote-performance` 응답에 포함된다.
- exact combo가 없으면 FPS 대신 데이터 없음과 이유를 반환한다.
- 모든 FPS 행은 evidence type, confidence, sampleCount를 가진다.

### 자동 견적

- AI 단독 선택 시 게임 해상도와 게임 목록이 결과를 강제로 지배하지 않는다.
- 게임+AI+영상 편집 혼합 입력이 각 workload 비중에 따라 CPU/GPU/RAM/저장장치에 반영된다.
- 450만원 AI 요청이 불가능하면 게이밍 PC로 대체하지 않고 부족 금액을 설명한다.
- 250GB~10TB+ 저장 요구를 표현할 수 있다.
- 예산·재고·호환성 조건을 통과한 실제 판매 단위만 결과에 포함된다.
- 결과 후보 3개가 서로 다른 목적을 가지며 차이를 설명한다.

### 추천 콘텐츠

- 공개 추천 글이 목적·가격대·플랫폼별로 중복 없이 생성된다.
- 추천 글의 가격은 현재 활성 판매 단위와 일치하거나 재검증 필요로 표시된다.
- 성능 근거가 없는 글에는 실측/검증 표현을 사용하지 않는다.
- 공개 응답에 내부 수집 출처와 원본 URL이 노출되지 않는다.

### 테스트

필수 fixture/e2e 시나리오:

1. 평균 FPS 하나만 있는 입력은 해상도별 실측 3행을 만들지 않는다.
2. FHD만 실측된 입력은 QHD/4K를 `DERIVED` 또는 `NONE`으로 처리한다.
3. `games=["APEX 레전드"]` 요청은 APEX 외 게임을 반환하지 않는다.
4. exact CPU/GPU가 아닌 family match는 실측 뱃지를 붙이지 않는다.
5. AI 단독·게임 단독·AI+게임 혼합 입력이 각각 다른 질문과 후보를 만든다.
6. 10TB 저장 요구가 SSD 1TB 결과로 조용히 축소되지 않는다.
7. 예산 상한을 넘는 후보는 기본 결과에서 제외된다.
8. 같은 목적·가격대·CPU/GPU 조합의 추천 글은 중복 생성되지 않는다.
9. 가격 또는 재고가 바뀐 추천 글은 게시 전 검수 대상으로 전환된다.

## 최종 판단

지금 필요한 것은 FPS 숫자를 더 많이 만들어내는 일이 아니라, **측정값·보고값·추정값을 분리하고, 자동 견적을 단일 용도/단일 우선순위 모델에서 복수 workload 기반 모델로 바꾸는 것**이다. 이 순서로 진행하면 현재의 “해상도별 동일 FPS”, “조합 1개”, “AI인데 게이밍 견적”, “추천 글 3개” 문제가 각각 데이터·엔진·콘텐츠 생성의 책임 위치에서 해결된다.
