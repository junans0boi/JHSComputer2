# 복수 workload 기반 자동 견적 설문·후보 생성 스펙

## Problem Statement

현재 자동 견적 설문은 하나의 용도, 하나의 해상도, 하나의 우선순위와 단일 예산만 입력받는다. 브라우저의 고정 템플릿이 상품을 선택하기 때문에 AI·영상편집·개발을 함께 원하는 사용자의 요구 비중을 표현할 수 없고, 예산이 큰 AI 요청이 일반 게이밍 구성으로 조용히 대체될 수 있다.

현재 결과는 실제 판매 단위·재고·가격·호환성·성능 근거를 하나의 후보 생성 규칙으로 검증하지 못한다. 데이터가 부족한 경우에도 부품이나 FPS를 채워 넣을 위험이 있어, 사용자가 결과를 검증하기 어렵다.

## Solution

사용자 입력을 `WorkloadProfile`, `BudgetProfile`, `PreferenceProfile`, `StorageDemand`로 정규화한다. 서버의 견적 미리보기 인터페이스가 실제 활성 판매 단위와 최신 가격·재고·표준 부품 스펙을 조회하고, 하드 제약을 먼저 통과시킨 뒤 목적별 점수로 균형형·성능 우선·가성비/확장형 후보를 만든다.

후보마다 선택 이유, 부족하거나 포기한 조건, 가격 구성, 호환성 결과, 성능 근거를 반환한다. 조건을 만족하는 후보가 없으면 `REVIEW_REQUIRED`와 미충족 조건을 반환하며 임의의 부품·가격·FPS를 생성하지 않는다.

## User Stories

1. 컴퓨터 구매자로서 여러 사용 목적을 함께 선택하고 각 목적의 비중을 입력하고 싶다. 그래야 게임과 영상편집을 함께 고려한 견적을 받을 수 있다.
2. 컴퓨터 구매자로서 용도 프리셋으로 빠르게 설문을 작성하고 싶다. 그래야 전문 지식 없이도 합리적인 기본값을 사용할 수 있다.
3. 고급 사용자로서 workload 비중을 직접 조정하고 싶다. 그래야 내 실제 사용 패턴을 정확히 반영할 수 있다.
4. 게임 사용자로서 게임 목록·해상도·주사율을 입력하고 싶다. 그래야 GPU 선택이 실제 플레이 목표를 반영한다.
5. AI 사용자로서 게임 질문을 받지 않고 로컬 추론, 모델 규모, 양자화, VRAM 요구를 입력하고 싶다.
6. 영상편집 사용자로서 사용하는 편집 프로그램, 타임라인 해상도, 코덱과 작업 강도를 입력하고 싶다.
7. 스트리머로서 출력 해상도와 하드웨어 인코딩 선호를 입력하고 싶다.
8. 개발자로서 Docker·가상머신 사용 여부와 개발 workload를 입력하고 싶다.
9. 사무 사용자로서 문서·회의·멀티태스킹 수준을 입력하고 싶다.
10. 구매자로서 목표 예산을 빠르게 입력하고 싶다.
11. 구매자로서 최소·목표·최대 예산과 Windows·조립·배송 포함 여부를 조정하고 싶다.
12. 구매자로서 최대 예산을 넘는 구성을 자동으로 받지 않고, 부족 금액과 완화 가능한 조건을 보고 싶다.
13. 구매자로서 운영체제, 현재 프로젝트, 보관 자료, 연간 증가량과 백업 요구를 입력하고 싶다.
14. 구매자로서 저장장치 수요가 큰 경우 단일 저용량 SSD로 조용히 축소되지 않기를 원한다.
15. 구매자로서 균형형·성능 우선·가성비/확장형 후보를 비교하고 싶다.
16. 구매자로서 각 후보가 왜 다른지, 어떤 조건을 포기했는지 알고 싶다.
17. 구매자로서 판매 가능한 실제 상품명·상품번호·현재 가격이 표시되기를 원한다.
18. 구매자로서 CPU 소켓, 메모리 타입, GPU 길이, 쿨러 높이, 메인보드 폼팩터와 파워 용량이 맞지 않는 후보를 받지 않기를 원한다.
19. 구매자로서 exact CPU/GPU 조합의 근거가 없으면 실측 FPS가 표시되지 않기를 원한다.
20. 구매자로서 보고값·추정값·실측값을 화면에서 구분하고 샘플 수와 신뢰 수준을 확인하고 싶다.
21. 구매자로서 조건을 만족하는 후보가 없을 때 데이터 부족인지 예산 부족인지 알고 싶다.
22. 구매자로서 검토 필요 상태에서 예산을 늘리거나 조건을 완화한 뒤 다시 계산하고 싶다.
23. 비로그인 사용자로서 결과를 브라우저에서 다시 열고 싶다.
24. 로그인 사용자로서 입력 프로필, 후보, 선택 이유와 가격 검증 시각을 서버에 저장하고 싶다.
25. 기존 사용자로서 이전 v1 견적을 새 설문을 거치지 않고 계속 열고 싶다.
26. 주문 사용자로서 주문 직전에 가격·재고가 바뀌면 승인 필요 상태를 안내받고 싶다.
27. 운영자로서 후보 생성 규칙 버전과 성능 근거를 추적하고 싶다.
28. 운영자로서 임의의 상품·가격·FPS가 공개 결과에 들어가지 않았음을 검증하고 싶다.

## Implementation Decisions

- 사용 프로필은 `GAMING`, `STREAMING`, `VIDEO_EDITING`, `AI`, `OFFICE`, `DEVELOPMENT` workload의 배열이며 비중 합계는 100%다. AI는 1차 범위에서 로컬 추론을 대상으로 한다.
- 예산 프로필은 최소·목표·최대 금액과 포함 항목을 가진다. 본체 부품·조립·배송·선택 Windows를 기본 범위로 삼고 모니터는 제외한다.
- 선호 프로필은 균형형·성능 우선·가성비/확장형 프리셋과 직접 조정 가능한 가중치를 제공한다.
- 저장장치 수요는 시스템·현재 프로젝트·보관·연간 증가·중복 보관 요구를 분리한다.
- 설문은 목표 예산, workload와 비중, 조건부 세부 질문, 게임/성능 조건, 저장장치 수요, 선호 순서의 단계형 흐름으로 제공한다. 선택하지 않은 workload 질문은 노출하지 않는다.
- 자동 견적의 외부 seam은 서버 견적 미리보기 인터페이스다. 서버는 실제 활성 `supplier_offers`와 최신 가격·재고, 표준 부품 스펙만 사용한다.
- 소켓·메모리·폼팩터·GPU 길이·쿨러 높이·파워 용량은 하드 제약이다. 하드 제약 실패 후보는 점수로 보정하지 않고 제외한다.
- 후보는 최대 3개를 반환한다. 후보가 부족하면 가짜 상품을 채우지 않고 `REVIEW_REQUIRED`와 실패 원인·완화 가능 조건을 반환한다.
- 후보 결과는 `rulesetVersion`, 선택 이유, 미충족 조건, 부품별 판매 단위와 가격 시각을 가진다.
- 성능은 exact combo만 실측 근거로 연결한다. `MEASURED`, `SOURCE_REPORTED`, `DERIVED`, `NONE`과 confidence·sampleCount를 함께 반환한다.
- 기존 v1 `QuoteInput`과 localStorage 데이터는 `profileVersion: 2` 사용 프로필로 변환하는 adapter를 통해 읽는다. 새 견적부터 v2 프로필을 사용한다.
- 서버 저장은 기존 견적 snapshot 구조를 확장해 입력 프로필·후보 선택·ruleset·evidence를 보존한다. 별도 프로필 테이블은 초기 범위에서 만들지 않는다.
- 비로그인 결과는 브라우저에 임시 저장하고, 로그인 사용자의 선택 후보는 서버 견적으로 저장한다. 주문 전에는 가격·재고를 별도 검증한다.
- 기존 추천 콘텐츠 자동 생성 전체 개편과 결제·배송 연동은 이 스펙의 범위에 포함하지 않는다.

## Testing Decisions

- 최우선 테스트 seam은 서버 견적 미리보기 인터페이스다. 내부 점수 함수나 SQL 구현이 아니라 외부 입력과 반환 행동을 검증한다.
- 서버 테스트는 AI 단독·게임 단독·혼합 workload, 예산 초과, 호환 실패, 판매 단위 없음, exact benchmark 없음, 저장장치 대용량 요구를 검증한다.
- 브라우저 테스트는 조건부 질문 노출, 비중 합계 100%, 후보 3개 비교, `REVIEW_REQUIRED`, v1 결과 재열기를 검증한다.
- API·브라우저 fixture는 실제 DB의 임의 상태에 의존하지 않고, 실제 판매 단위·스펙·evidence를 표현하는 독립 fixture를 사용한다.
- 기존 v1 견적과 새 v2 견적이 모두 열리는 호환성 테스트를 추가한다.
- typecheck, build, API smoke test, 주요 견적 화면 브라우저 QA, 로그인 사용자의 저장·주문 전환을 완료 기준에 포함한다.

## Out of Scope

- 토스페이먼츠 결제 연동
- 배송사 실시간 API
- AI 모델 학습·파인튜닝용 워크스테이션 최적화
- 추천 콘텐츠 자동 생성 P4 전체 개편
- 외부 사이트 게시글의 신규 대량 수집
- 운영 DB destructive reset

## Further Notes

이 스펙은 기존 고정 템플릿을 한 번에 삭제하는 작업이 아니다. v1 adapter를 먼저 제공하고, 서버 후보 미리보기와 UI를 수직 슬라이스로 도입한 뒤, 모든 caller가 v2를 사용하게 된 시점에만 기존 경로를 제거한다.
