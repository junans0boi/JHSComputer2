# ADR-019: 출처가 다른 FPS를 공용 관측값 테이블에 적재

작성일: 2026-09-10
상태: 수락됨
관련 Wayfinder: #63
관련 스펙: `docs/specs/2026-09-unified-kjwwang-computerbase-fps-ingestion.md`

## 문맥

ComputerBase는 테스트 시스템과 차트 조건이 있는 공개 벤치마크이고, 견적왕은 견적
상세 페이지에서 CPU·GPU 조합별 게임 추천 성능을 제공한다. 두 출처 모두 동일한 게임
성능 화면에서 활용해야 하지만, 근거의 의미가 다르다. 별도 FPS 테이블을 만들면 API와
집계가 이중화되고, 하나의 화면에서 조합을 비교하기 어렵다.

## 결정

1. 두 출처의 숫자 FPS는 `benchmark_fps_results`에 함께 저장한다.
2. 조합 집계는 `benchmark_combo_game_results`를 공동 사용한다.
3. 두 테이블에 `EVIDENCE_TYPE`을 추가해 `SOURCE_BENCHMARK`, `SOURCE_RECOMMENDATION`,
   `MEASURED`를 구분한다.
4. `SOURCE_CONDITION_KEY`는 ComputerBase 기사/테스트 조건 또는 견적왕 `es_sn`을
   가리키는 provenance 키로 사용한다.
5. 견적왕 숫자는 원문 추천값으로 공개하되, JHS 실측이나 ComputerBase 차트로 포장하지
   않는다. 샘플 수가 1이라는 이유만으로 모든 값을 임의로 해상도 복제하거나 평균하지
   않는다. 동일 조건의 최신 대표값은 원문 수정일, 견적 ID, 수집 시각, DB ID 순으로
   결정한다.
6. 기존 API와 선택기는 공용 집계 테이블을 읽고, 근거 유형은 응답에 포함한다.

## 이유

- 고객 화면은 CPU/GPU 조합별 성능을 하나의 표에서 조회해야 한다.
- 출처별 테이블을 분리하면 조합 선택·최신값·중복 제거 규칙이 두 군데로 갈라진다.
- `EVIDENCE_TYPE`과 원본 조건을 함께 보존하면 저장은 통합하면서 표시·검증은 분리할 수 있다.
- 현재 견적왕 HTML 파서는 이미 페이지 본문의 해상도별 숫자 FPS를 읽을 수 있으므로,
  기존 동기화 경로의 하드코딩과 삭제 동작을 제거하는 것이 가장 작은 변경이다.

## 결과

- `benchmark_builds`는 출처별 원본 견적/기사 단위를 보존한다.
- 동일 조합의 최신 대표값은 집계 테이블에서 선택하되, 과거 원본은 삭제하지 않는다.
- 프론트는 FPS·체감 등급을 우선 표시하고, 필요할 때 근거 유형을 표시할 수 있다.

## 기각한 선택

- 견적왕 FPS를 ComputerBase 실측값으로 합치기: 근거 수준을 훼손한다.
- 견적왕만 별도 FPS 테이블에 저장하기: 공용 조합 선택과 집계를 중복 구현하게 된다.
- 원문에 없는 FPS를 해상도별로 복제하기: 잘못된 성능 차이를 만든다.
